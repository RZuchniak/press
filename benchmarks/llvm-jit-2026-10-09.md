# Initial LLVM JIT measurements: 2026-10-09

Windows/amd64, AMD Ryzen 5 3600X, Go 1.27.2, LLVM 23.1.3, GOMAXPROCS=12.
Three samples per benchmark with `-benchtime=150ms`. Times below are medians for
one complete workload, usually containing 1,000 loop iterations. Every execution
checks its result against the existing workload expectation.

| Workload | VM (ms) | LLVM (ms) | Observed LLVM result |
| --- | ---: | ---: | --- |
| Lists | 0.638 | 9.743 | 15.3x slower |
| Maps | 0.777 | 10.426 | 13.4x slower |
| Empty program | 0.000247 | 0.001258 | 5.1x slower |
| Arithmetic | 0.095 | 0.0089 | 10.7x faster |
| Function calls | 0.283 | 6.061 | 21.4x slower |
| Nested value copies | 0.911 | 7.348 | 8.1x slower |
| Shared references | 0.333 | 6.167 | 18.5x slower |
| Interface dispatch | 0.349 | 7.015 | 20.1x slower |
| Allocation | 0.345 | 5.180 | 15.0x slower |

Raw output: [LLVM and VM benchmarks](llvm-jit-windows-amd64.txt).

The arithmetic workload qualifies for scalar lowering: primitive locals, operand
stack and instruction charging stay native. Other loop workloads contain object
operations or guest calls and therefore use frequent Go callbacks. These results
support the scalar path as an experiment, but not making LLVM the default backend.

Compiled functions containing guest calls currently use the helper path even if
all values are primitive. Calls cross native/Go boundaries and create registered
frames. The object helper path also starts from unoptimized instructions, so it
does not gain the VM's fused field-read optimizations that avoid copying enclosing
values. This explains some additional allocations in copy-heavy workloads.

CompileLLVM followed by Close took a median of 15.13 ms for the simple counter
loop, excluding Press source compilation. This includes LLVM library/context/JIT
setup, preparation, IR emission, verification, code materialization and disposal.
It is measured separately from warmed execution and is not an end-to-end CLI
startup measurement. A small one-shot program will not benefit from the measured
warmed arithmetic improvement once this overhead is included.

The standalone `BenchmarkLLVMArithmetic` counter loop, sampled separately with
`-benchtime=200ms`, took medians of 53.0 us in the VM and 5.6 us in LLVM. It has less
arithmetic than the standard workload. Do not combine the two into one estimate.

Allocation statistics in the raw Go benchmark output cover the Go heap. They do
not measure LLVM's native code memory, allocator traffic or process RSS. Native
memory measurements and sustained guest allocation tests remain follow-up work.

## Reproduce

```powershell
.\scripts\go.ps1 test ./internal/language -run '^$' -bench 'BenchmarkLLVMWorkloads|BenchmarkLLVMCompile' -benchtime=150ms -count=3
```

Set PRESS_LLVM_DLL or install the compatible repository-local library as described
in [LLVM setup](../docs/llvm.md). The benchmark explicitly skips when no library is
configured or locally available.

## Validation

All Go tests and go vet passed. Native tests compare historical execution fixtures,
all four main example programs, partial budgets, recursion limits and arithmetic
boundaries. Forced-GC tests preserve live objects through native callbacks and
check release of a dead root during execution. Tests also cover independent
concurrent runs, callback failures, frame cleanup and execution of an artifact
after its source has been deleted.

The 64 historical cases also passed through the normal built CLI. The default
vm.go is unchanged: the initially measured overhead from a shared dispatch
refactor was removed before these final measurements. Native helper semantics
are generated from that VM source instead.
